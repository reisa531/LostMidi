# 数据库与迁移

PostgreSQL 保存档案元数据，文件二进制由 Backend 的 storage abstraction 管理。业务代码使用参数化 SQL，不让 Next.js 连接数据库。

## 表与关系

| 表 | 用途与关系 |
| --- | --- |
| `midi_entries` | 作品 / 档案，`slug` 是唯一公开定位符；年代可空，描述可空。 |
| `people` | 作者、编曲者、网站维护者或贡献者，不等同于未来的登录账户。 |
| `person_aliases` | 人物历史昵称；同一人物的同名昵称唯一，保留大小写。不同人物可以使用同一昵称。 |
| `midi_credits` | 作品与人物的多对多署名；主键为 `(midi_id, person_id, role)`，允许一个人有多个角色。 |
| `midi_files` | 一个作品的多个二进制版本；全局唯一的小写十六进制 `sha256`、唯一 `storage_key`、正数 `file_size`。 |
| `historical_sources` | 网站名称、历史 URL、观察时间范围、可选 Wayback URL 与备注；不调用外部服务。 |
| `recovery_events` | 可空的寻回时间、可空的贡献者外键、过程叙述与可空的文本证据；created_at 保留记录创建时间。 |
| `admin_sessions` | 管理员会话令牌摘要、凭据标识与有效期；账号可来自数据库安装或环境覆盖，与人物分离。 |
| `site_installation` | 005 新增，单行 `id=1` 持久安装标记、站点名称/简介及认证来源；数据库安装时保存管理员用户名与密码哈希。 |
| `midi_import_objects` | 006 新增对象 journal；跟踪待清理对象摘要、存储 key 和触碰时间，不通过列桶发现孤立对象。 |
| `midi_creation_requests` | 007 新增创建请求身份与提交摘要；008 将唯一作品关联改为可空，删除作品后保留回执。 |
| `admin_audit_log` | 010 保存管理员删除与恢复操作；作品和人物通过 `deleted_at` / `deleted_by` 进入回收站。 |

当前生产应用到 008；本分支新代码要求迁移至 `011_cleanup_retry_metadata.sql`。009 提供 `pg_trgm` 搜索索引，010 提供可恢复删除与审计，011 提供外部对象清理重试信息。本次没有部署或验证；生产迁移前须执行独立恢复演练。

迁移 `002_admin_sessions_and_revision.sql` 增加 `admin_sessions`，以 64 位小写十六进制 `token_hash` 为主键，不存原始令牌。会话有效 8 小时，凭据标识由当前选用的用户名与哈希决定；不匹配的会话被拒绝，但恢复旧凭据可能让未过期的旧会话再次匹配，并非永久撤销。

该迁移同时新增 `midi_entries.revision`：创建为 1，每次更新由触发器递增。后台更新 SQL 同时匹配 id 与读取时的 revision，旧版本返回冲突。后台署名、来源及寻回写入均先更新父作品 revision，再在同一事务修改子记录；直接 SQL 修改子表不自动触发父作品版本。

领域实体的生成 ID 使用 `BIGINT GENERATED BY DEFAULT AS IDENTITY`；`site_installation.id` 是固定为 1 的 SMALLINT 主键，不使用 identity 序列。API 将领域 ID 作为字符串传输，避免 JavaScript 对大整数的精度问题。`estimated_year` 单独表达推测年份，未知时使用 `NULL`，不填造假的 1 月 1 日。事件时间使用 `TIMESTAMPTZ`；迁移 004 后寻回时间也可为空，来源时间已有完整范围必须满足先后顺序。历史事实若只知道年份，应在备注表达不确定性，而不是暗示精确日期。`midi_entries.updated_at` 由数据库触发器维护；当前管理服务会在修改子记录的同一事务内更新作品时间，直接 SQL 子表变更不会自动更新它。

署名角色暂定为 `composer`、`arranger`、`sequencer`、`contributor`。状态字段采用文本加 CHECK 约束，新增值通过后续 SQL migration 更新约束，不引入 PostgreSQL enum 类型。档案状态允许 `archived`、`partially_recovered`、`lost`、`uncertain`；这些是人工维护的档案判断，当前不从文件行数自动推导。

MIDI 和人物进入回收站时只更新 `deleted_at` / `deleted_by`，不删除子记录、文件登记、人物关系或对象。公开查询排除软删除行；管理员可在回收站恢复。人物仍被署名或寻回引用时 API 会拒绝移入回收站。删除与恢复在同一事务写入 `admin_audit_log`，保留操作人、时间、对象类型、编号和标签。不要绕过 Service 直接删除业务记录。

全局 `UNIQUE(sha256)` 将完全相同的二进制限制为一条文件记录，因此同一文件当前归属一个档案。若将来发现跨作品复用的真实需求，再拆分 object 表和作品文件关联表。当前由后端计算并规范化 SHA-256，数据库唯一约束是处理并发写入的最终防线。存储 key 是存储接口的标识而非下载 URL，路径安全由本地存储实现验证。

## 一次性安装与持久锁

新增 `database/migrations/005_site_installation.sql` 只创建 `site_installation`，不改旧迁移，也不创建数据库或 seed。表至多有一行；没有记录表示尚未持久安装，`id=1` 记录一旦提交就是安装锁，而不是内存标记或环境变量开关。

| 字段 | 规则 |
| --- | --- |
| `id` | SMALLINT 主键，默认 1，CHECK 限定只能为 1 |
| `site_name` / `site_description` | 站点名称与简介；API trim 后分别为 1–200 / 0–1000 UTF-8 字节 |
| `auth_source` | `database` 或 `environment` |
| `username` / `password_hash` | `database` 时均非 NULL；用户名为 ASCII `[A-Za-z0-9_.-]{3,64}`，哈希为随机盐 PBKDF2-HMAC-SHA256、600,000 次；`environment` 时两列均为 NULL，不复制部署凭据 |
| `installed_at` | TIMESTAMPTZ，记录安装时间 |

安装 API 在同一事务保存站点设置与数据库管理员，主键约束保证并发只有一个安装成功；响应等待 commit 确认。超时或连接中断不能证明回滚，必须刷新状态核对，不能删除记录后重试。安装后移除后端 `INSTALLATION_TOKEN`、重启进程或更换浏览器均不解锁；没有重装/reset 接口，不得通过删除表或安装行恢复密码。

旧环境部署第一次运行新版时必须保留完整有效的 `ADMIN_USERNAME` + `ADMIN_PASSWORD_HASH`：启动会写入 `auth_source=environment` 的持久 legacy 标记。移除环境凭据后仍为 installed，但因标记不存账号哈希而禁用登录；需恢复环境凭据或由维护者提供应急覆盖。升级前已移除凭据时，系统无法推断这个库曾经安装。

完整有效的环境凭据始终优先于数据库管理员，但不改数据库站点设置或账号。无完整覆盖时读取数据库账号，默认 `ADMIN_USERNAME=admin` 与空哈希不会遮盖它。无完整环境覆盖时，每次登录及鉴权重新读取数据库凭据；选用的用户名与哈希决定会话 identity。切换期间不匹配的 session 被拒绝；恢复旧凭据可能重新启用尚未过期的旧 session，不能视为永久撤销。

启动与 `/ready` 必须同时确认 005 迁移记录和 `site_installation` 表可查询，并继续核对 004 记录及 `recovered_at` 实际可空。数据库故障应返回 503，而不是被解释为未安装；连接和全部迁移仍由部署者准备，安装页不自动完成它们。

生产备份现在可能包含数据库管理员密码哈希，不能只保护 `.env` 中的哈希；数据库归档、环境配置及会话摘要均需受控权限和加密。恢复时应明确撤销历史 `admin_sessions`，或使用不同于历史的有效凭据，并防止以后恢复旧凭据重新启用旧会话。忘记密码可用 `scripts/admin_password.py` 生成新的环境应急覆盖，保持覆盖直至妥善维护数据库凭据；这不会自动永久重置数据库账号。恢复流程见 [RUN.md](../RUN.md)。

## 版权字段

版权信息当前存放于作品级别，供将来审核流程使用：

| 字段 | 值或含义 |
| --- | --- |
| `copyright_status` | `unknown`（默认）、`public_domain`、`licensed`、`copyrighted`。 |
| `license` | 可空的许可证名称或标识。 |
| `rights_holder` | 可空的权利人文字记录；不强行关联到人物表。 |
| `distribution_permission` | `unknown`（默认）、`permission_granted`、`metadata_only`、`restricted`。 |

版权归属和分发许可分别表达，存在于 archive.org 不代表 public domain。当前不自动判断法律权利。管理员导入要求明确确认公开分发；访客下载需文件确认且作品未标为 `restricted` / `metadata_only`，并校验归属、大小和 SHA-256。版权字段不会自动给予下载许可。如果不同文件版本需要不同许可，后续 migration 可在文件级别补充覆盖信息。

## 迁移运行方式

使用 PostgreSQL 自带的 `psql` 和 POSIX shell；Linux、macOS、WSL 或 Git Bash 均可。另外需要 `sha256sum`（GNU / PostgreSQL Docker image）或 `shasum`（macOS）。连接使用标准 libpq 环境变量：

```sh
export PGHOST=localhost PGPORT=5432 PGDATABASE=lostmidi PGUSER=lostmidi
export PGPASSWORD='your-local-password'
sh database/migrate.sh
```

也可提供 `DATABASE_URL`。不要把含密码的实际连接串提交到版本控制。

`migrate.sh` 按 `NNN_description.sql` 文件名顺序执行 `database/migrations/*.sql`。整个运行位于一个事务中，事务级 advisory lock 防止并发 runner 同时创建 schema。`schema_migrations` 记录每个已应用文件名、SHA-256 和应用时间；重复运行跳过已有版本，已应用文件被修改时直接报错并回滚。**已应用的 migration 不要修改或重新编号，应新增下一个文件。** 不要从目录删除已经应用的迁移；版本历史是仓库的一部分。

脚本不会依赖 PostgreSQL 的 `/docker-entrypoint-initdb.d`，因此已有 persistent volume 也可以应用新迁移。Compose 的迁移服务每次启动会再次运行 runner；Backend 应在迁移成功后启动。迁移脚本自身不要包含 `BEGIN`、`COMMIT`、psql shell 命令或需要事务外执行的语句（例如 `CREATE INDEX CONCURRENTLY`）。当前只提供向前迁移；发布环境运行前应做好数据库备份和恢复演练。

## 可选虚构示例

```sh
SEED_DEMO=true sh database/migrate.sh
```

默认 `SEED_DEMO=false`，环境模板也默认关闭。示例脚本独立放在 `database/seeds/`，通过 `schema_seed_history` 记录一次性执行与校验和，重复运行不会添加重复数据。开发环境按需显式开启，CI 显式开启；生产环境保持 false。先迁移空库，再按需开启示例同样可行。关闭 seed 不会移除此前写入的数据。上线前使用 `psql -X -f database/check_production.sql` 只读检查已知演示和测试标记，再人工复核资料。

示例包含三条纯虚构档案：`example-midi`、`clockwork-tide`、`lantern-map`；两位虚构人物及其昵称、历史来源、寻回叙述。所有网站使用保留的 `example.invalid`，没有声明任何真实 Wayback capture。示例只寻回了虚构的文字元数据，没有提供 MIDI 二进制，因此 **`midi_files` 保持空表**；详情页应明确呈现暂无文件。状态依次为 `partially_recovered`、`lost`、`uncertain`，分发策略为 `metadata_only`，不使用真实音乐或虚构文件散列冒充文件。

## 数据库约束检查

在完成 migration 的专用测试数据库中运行：

```sh
psql -X -v ON_ERROR_STOP=1 -f database/tests/constraints.sql
```

脚本验证重复 SHA-256、非法散列、零字节文件、非法档案状态、人物署名保护、空寻回日期、来源时间顺序、寻回贡献者移除、从属元数据删除，以及会话摘要格式、revision 初始值和自动递增；005 另有安装单行及认证来源/凭据约束检查。测试在事务内执行并回滚所有行；PostgreSQL identity 序列可能仍递增，这是正常行为。它不会检查文件是否物理存在，也不替代 Service 和存储层单元测试。

CTest 的 installation 集成测试会创建隔离 schema，连接用户需具备 CREATE SCHEMA 权限；`LOSTMIDI_TEST_DATABASE_URL` 仍要求已迁移且含 demo seed 的专用测试库。HTTP 与浏览器安装 smoke 不使用这种回滚隔离：`scripts/installation_smoke.py` 和 `scripts/installation_browser_smoke.py` 各自要求全新、已迁移、独立的专用测试库，且会永久写入安装锁，不能先后指向同一个库。命令与测试环境变量见 [RUN.md](../RUN.md)。本地验收结果及尚未执行的部署检查见 [Implementation Report](implementation-report.md)。

## 人物与署名写入

迁移 `003_person_revision.sql` 为人物增加正整数 revision 与 UPDATE 自动递增触发器。人物简介与完整昵称列表在同一事务保存；昵称保持大小写，允许不同人物使用相同昵称。后台人物写入必须携带旧 revision。

署名保存整体替换当前作品的署名列表，使用作品 revision 防止覆盖其他编辑。事务锁定作品、检查人物外键并写入署名，未知人物或任何失败都会回滚署名和 revision。允许同一人物承担不同角色，禁止重复 `(person_id, role)`。空列表明确表示移除所有署名。人物删除接口还会检查寻回引用，只有全部引用解除后才能删除。

## 来源与寻回写入

迁移 `004_optional_recovery_date.sql` 仅移除 `recovery_events.recovered_at` 的 NOT NULL，不改写已有值，也不修改旧迁移文件。当前后端启动及 `/ready` 同时核对 schema_migrations 中的 004 记录与实际列可空性。

管理读取先在事务中 `FOR SHARE` 锁定父作品，再用同一连接读取 revision、来源及寻回。写入先通过父作品 revision 条件 UPDATE 取得锁，再逐条修改归属于该作品的子记录；人物外键使用 `FOR KEY SHARE` 校验。失败回滚父作品版本与子记录，提交确认后才响应。编辑保留子记录 ID 及寻回 created_at；不会自动改变归档状态或署名。

来源和寻回日期在 API 中使用 UTC 六位小数精度，未知时间和人物为 null；可空的寻回日期排列在已知日期之后。evidence 为自由文本，不是来源外键或文件附件。具体请求字段和错误码见 [Admin 文档](admin.md)。


## 原子建档与请求回执（007–008）

`007_midi_creation_requests.sql` 增加 `midi_creation_requests`：UUID v4 请求键、规范化提交内容的 SHA-256、唯一关联的作品 ID。回执与作品及可选文件在同一事务提交。相同键和内容返回已有作品，不重复创建或重新添加文件；相同键但不同内容返回 `409 IDEMPOTENCY_CONFLICT`。

`008_deleted_creation_receipts.sql` 将 `midi_id` 改为可空，并将其外键从级联删除改为 `ON DELETE SET NULL`。删除作品后保留请求键及摘要；相同内容重放返回 `410 CREATION_DELETED`，不能让旧请求复活已删除作品，不同内容重放仍返回幂等冲突。

写对象前仍独立提交 006 journal；存储或数据库提交失败时保留 journal 供既有安全清理处理，不直接删除对象。新建作品初始 revision 为 1；后续编辑、署名与文件导入沿用现有版本控制。007 和 008 不更改条目 ID 类型、已有资料或安装锁。

新版启动与 `/ready` 要求 008 账本、`midi_id` 实际可空及保留回执的外键，并保留 007 及更早检查；即使关闭导入也需要迁移。当前工作区另要求 010 回收站列与审计表、011 清理尝试列。使用现有 runner 校验已应用文件并跳过，不手工重复执行裸迁移 SQL。

## 搜索索引与回收站

009 启用 PostgreSQL `pg_trgm`，为作品标题、slug、人物姓名、历史昵称和来源名称创建 GIN trigram 索引。目录 API 对查询词做参数绑定，转义 `!`、`%`、`_` 后执行子串匹配；分页结果、筛选和排序仍由 PostgreSQL 执行。

010 增加 `midi_entries.deleted_at/deleted_by`、`people.deleted_at/deleted_by` 和 `admin_audit_log`。移入回收站先 `FOR UPDATE` 锁定记录并核对 revision，然后在同一事务写软删除标记和审计记录。人物仍被署名或寻回事件引用时返回 `409 PERSON_IN_USE`。MIDI 文件及所属来源、署名和寻回记录保留，恢复只清除删除标记并由触发器增加 revision；恢复操作也写入审计记录。

公开目录、详情、人物和下载查询排除软删除行。删除 MIDI 不再加入对象清理 journal，因为文件仍被回收站记录引用；因此对象继续可恢复。011 为现有导入孤儿 journal 添加尝试次数、最近尝试时间和通用失败代码；对象删除失败后事务保留 journal，之后显式 `--cleanup-imports` 可重试。清理仍要求超过 24 小时、没有引用、每次最多 100 条，必须匹配原数据库和存储配置，禁止在生产试运行。
